# Проєктування лабораторної роботи №4

Дата фіксації проєктування: 2026-11-09. Цей документ створено до змін реалізації лабораторної роботи №4.

## 1. Межі роботи та параметри варіанта

- Предметна сутність: направлення на дослідження, ресурс `/referrals`.
- Варіант: 2.
- Максимальна кількість воркерів: `R=5` (із лабораторної роботи №3).
- Розмір синтетичного зрізу: `S=256`.
- Квантилі: `q_lo=0,05`, `q_hi=0,95`.
- Інтервал опитування: `T_poll=100 мс`, якщо окремий експеримент не вимагає `1 мс`.
- Lease: `L=5 с`; heartbeat кожні `L/3` секунди.
- Сценарій відмови: Ф3 — десять задач із `seed=0`, для яких обробка завершується винятком.
- Додаткова вимога: Д1 — пріоритет задач від 1 до 3 і захоплення за `priority DESC, created_at`.
- `FAIL_RATE=0` у кроках 2–8 і `FAIL_RATE=0,15` у кроці 9.

## 2. Структура даних

### `tasks`

| Поле | Тип і обмеження | Призначення |
| --- | --- | --- |
| `id` | `BIGINT IDENTITY PRIMARY KEY` | Ідентифікатор задачі |
| `record_id` | `BIGINT NOT NULL REFERENCES referrals(id)` | Направлення, яке отримує воркер через HTTP |
| `status` | `VARCHAR`, `queued/running/done/failed` | Стан задачі |
| `priority` | `SMALLINT CHECK 1..3` | Д1 |
| `seed` | `BIGINT CHECK 0..2^31-1` | Детермінований зріз; `0` є отруєною задачею Ф3 |
| `attempts` | `INTEGER >=0` | Кількість захоплень |
| `max_attempts` | `INTEGER >0 DEFAULT 3` | Межа повторів |
| `token` | `BIGINT >=0` | Fencing token |
| `lease_until` | `TIMESTAMPTZ NULL` | Кінець володіння |
| `worker_id` | `VARCHAR NULL` | Поточний власник |
| `created_at` | `TIMESTAMPTZ` | Створення |
| `started_at` | `TIMESTAMPTZ NULL` | Останнє захоплення |
| `finished_at` | `TIMESTAMPTZ NULL` | Завершення |

Індекси: `(status, priority DESC, created_at, id)` для захоплення; `(record_id)` для зв'язку. Для наївного експерименту первинний ключ `task_results.task_id` тимчасово замінюється звичайним індексом окремою керованою командою; після серії обмеження відновлюється.

### `task_results`

`task_id` — первинний ключ у фінальній схемі, `token`, `worker_id`, `result JSONB`, `created_at`. Фінальний запис: `INSERT ... ON CONFLICT (task_id) DO NOTHING`; запис результату й перехід задачі у `done` виконуються в одній транзакції з перевіркою `token`.

## 3. API

- `POST /referrals/{id}/tasks` — `202`, повне тіло створеної задачі; `404`, якщо направлення не існує. Тіло може задавати `priority` 1..3 і тестовий `seed`; без `seed` сервіс генерує ненульове значення.
- `GET /tasks/{id}` — стан задачі та результат, якщо він існує; `200/404`.
- `GET /tasks` — `status`, `limit`, `offset`; відповідь містить `items`, `total`, `limit`, `offset`.
- Ідентифікатори обмежуються діапазоном PostgreSQL `BIGINT` на межі API.
- `priority` та `seed` перевіряються до звернення до БД.

Журнал API зберігає метод, шлях, тіло запиту, HTTP-код, заголовки та повне тіло відповіді.

## 4. Архітектура

- Web залишається окремим FastAPI Deployment. Фоновий цикл кожні 5 секунд повертає прострочені lease та оновлює `tasks_queued` і `tasks_running`.
- Worker є окремим Python-процесом і окремим образом. Він має HTTP `/metrics`, один послідовний виконавець і окремі фонові heartbeat/metrics tasks.
- Режими захоплення задаються конфігурацією: `naive`, `skip_locked`, `locked`; розмір пакета `CLAIM_BATCH_SIZE=1/10`.
- Нормальний режим: одна SQL-команда `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT b) RETURNING ...` у транзакції.
- Наївний режим навмисно розділяє `SELECT` та `UPDATE`, щоб відтворити гонку.
- Heartbeat і всі зміни задачі містять `id AND token`; нуль оновлених рядків означає втрату володіння.
- `SIGTERM`: припинити нові захоплення, завершити поточну задачу в межах grace period, повернути невиконані задачі пакета умовним `UPDATE ... AND token=...`, вийти з кодом 0.
- `seed=0` навмисно викликає виняток обробки; задача повторюється до `max_attempts`, після чого стає `failed`.
- Падіння за `FAIL_RATE` відбувається після CPU-кроку й до запису через `os._exit(1)`.

## 5. Обчислення зрізу

Використовується точний LCG із завдання. Обчислення виконуються циклами Python без NumPy/Numba. Результат: `p_lo`, `p_hi`, кількість вилучених пікселів, середнє і стандартне відхилення ненульових перетворених значень. Округлення реалізується цілочисельно як найближче ціле без залежності від banker's rounding.

## 6. Метрики

### Воркер

- `worker_tasks_total{result="done|failed|lost"}` — кількість остаточних подій відповідного типу.
- `worker_claims_total{result="task|empty"}` — кількість повернених задач або порожніх спроб.
- `worker_task_duration_seconds{step="claim|fetch|process|store"}` — гістограма тривалості кроку від монотонного старту до завершення кроку.
- `worker_tasks_in_flight` — поточна кількість задач, якими володіє процес, включно з невиконаним хвостом пакета.

### Пропускна здатність `X(W)`

- Чисельник: задачі, що вперше перейшли у `done` у вимірювальному вікні.
- Знаменник: фактична тривалість перетину останніх 30 секунд із інтервалом непорожньої черги, у секундах.
- Одиниці: успішно завершені задачі/с.
- Помилки, повторні обробки та `failed` не входять у чисельник і рахуються окремо.
- Первинне джерело: часові мітки `tasks.finished_at`, посекундні знімки БД і Prometheus.
- Якщо 400 задач спорожніють швидше ніж за 30 секунд, це фіксується як методичне обмеження; вікно не підмінюється штучною затримкою.

Розкид — вибіркове стандартне відхилення кількості `done` за фактичними односекундними інтервалами. `p99 claim` береться з raw-подій воркера, а не з агрегованих p99. Транзакції/с і CPU БД інтегруються за фактичними timestamps Prometheus.

### Закон Літтла

- `lambda`: кількість створених задач із `created_at` у останніх 120 секундах / фактична тривалість вікна.
- `W_q`: середнє `started_at-created_at` для задач, створених у цьому вікні.
- `L_q`: незалежний середньозважений за часом ряд `COUNT(*) WHERE status='queued'`, знятий з фактичними timestamps; це не похідна від `W_q`.
- Розбіжність: `abs(L_q-lambda*W_q)/L_q*100%`.

### Дублі

`D = n_dup/n`, де `n_dup` — кількість різних `task_id`, що мають більше одного результату або більше одного журналу `done`; `n` — кількість задач серії. Обидва джерела виводяться окремо.

### USL

Для `W=1,2,5`: `C(W)=X(W)/X(1)`, `y=W/C(W)-1`, `u=W-1`, `v=W(W-1)`. У звіті наводяться рядки, суми нормальних рівнянь, початкові оцінки, правило проєкції від'ємних коефіцієнтів на межу й `W*=sqrt((1-sigma)/kappa)` лише коли параметри дозволяють таку інтерпретацію.

## 7. Експерименти й докази

1. Міграція/API/метрики: unit/regression tests, HTTP-журнал, SQL introspection, Prometheus exposition.
2. Один воркер, 20 задач: raw-події кроків і середні `t_io`, `t_cpu`.
3. Наївне захоплення, `R=5`, 300 задач при 100/с: `T_poll=100 мс` і `1 мс`; SQL та worker logs дають `D`.
4. `SKIP LOCKED` при 1 мс і `FOR UPDATE` без `SKIP LOCKED`: `D`, raw claim latency, empty claims, щосекундні `pg_stat_activity/pg_locks`.
5. Lease/fencing: два воркери, 100 задач, `STOP` на `2L=10 с`, `CONT`; знімки задачі до/після, журнал stale token, рівно один результат.
6. `W=1,2,5`, по 400 задач: raw snapshots, X/SD/p99, DB TPS/CPU, `C(W)`, USL, графік; порівняння X(1) з `1/(t_io+t_cpu+T_poll/2)`.
7. Little: `0,7*X(5)` 180 с і overload `1,3*X(5)` 120 с; фактичні моменти вибірок, незалежне `L_q`.
8. Rollout restart під `0,7*X(5)`: termination states, returned/failed/duplicates/attempts>1.
9. `FAIL_RATE=0,15`, baseline і Ф3: 300 с на `0,7*X(5)`, десять `seed=0` посередині; restart counts, attempts distribution, `failed` проти `f^3`, X, p99 решти задач, timeline.
10. Д1: рівні частки пріоритетів 1/2/3 при `1,3*X(5)`; `W_q` окремо для кожного пріоритету та перевірка порядку захоплення.
11. Д4 із варіанта таблиці не застосовується; для варіанта 2 виконується лише Д1.

Оскільки 400 задач на виміряному стенді вичерпуються швидше ніж за 30 секунд,
серії з рівно 400 задачами зберігаються як обов'язкові прогони завдання, а окремо
виконуються підтверджувальні серії `capacity30` зі збільшеним початковим backlog.
У них визначення `X(W)` лишається тим самим, але непорожня черга існує протягом
повного 30-секундного вікна. Результати двох типів серій не змішуються.

Для 300-секундних failure-прогонів sampler оновлюється під час запуску, а на межі
вимірювання до контрольованого drain зберігаються повний знімок задач, розподіл
`attempts`, стани pod і журнали. Діаграма Ф3 будується з цих фактичних вибірок і
має вертикальну позначку моменту додавання poison-задач.

Кожний запуск має `run_id`, конфігурацію, UTC timestamps, команди, версії образів/інструментів, raw JSONL, SHA-256, summary та окремий файл похідного аналізу. Серії різних версій не змішуються.

## 8. Критерії приймання

- Усі API-коди й тіла відповідають контракту, включно з межами BIGINT і невалідними priority/seed/status.
- Наївний режим фактично створює дублювання або чесно фіксує, що в конкретному прогоні воно не відтворилося; результат не вигадується.
- `SKIP LOCKED` дає `D=0` за БД і журналами.
- Stale worker не може продовжити lease або записати результат зі старим token.
- У фінальному режимі `task_results` має первинний ключ, а duplicate result count дорівнює нулю.
- Усі таблиці/графіки відтворюються з raw скриптом; незалежний verifier не імпортує основний аналізатор.
- Генератор проходить окремий контроль і не приховує schedule lag/чергу/помилки.
- Звіт розділяє факти, вимірювання, інтерпретації та обмеження.
