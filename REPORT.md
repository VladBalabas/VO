## 1 Схема таблиці

Таблиця `referrals` містить одну предметну сутність.

| Поле | PostgreSQL тип | Обов'язковість і правило | Обґрунтування |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | первинний ключ, генерується базою | великий діапазон і відсутність залежності від пам'яті web інстансу |
| `patient_code` | `VARCHAR(64)` | `NOT NULL`, непорожній після обрізання пробілів | код не потребує необмеженого текстового поля |
| `modality` | `VARCHAR(3)` | `NOT NULL`, тільки CT, MRI, XR, US, PET | найдовше допустиме значення має три символи |
| `priority` | `SMALLINT` | `NOT NULL`, від 1 до 5 | діапазон малий |
| `doctor` | `VARCHAR(120)` | `NOT NULL`, непорожній | достатня довжина для ПІБ або службового позначення |
| `issued_at` | `DATE` | `NOT NULL` | час доби за умовою не потрібний |
| `status` | `VARCHAR(20)` | `NOT NULL`, created, scheduled, completed або cancelled | контрольований набір станів |

Індекс `idx_referrals_status` створено для фільтра переліку за статусом. Обмеження присутні одночасно на рівні FastAPI та PostgreSQL.

## 2 Таблиця спроєктованого API

Звичайне тіло направлення без `id`:

```json
{
  "patient_code": "PAT-0001",
  "modality": "MRI",
  "priority": 2,
  "doctor": "Лікар",
  "issued_at": "2026-10-11",
  "status": "created"
}
```

| Метод і шлях | Запит | Успішна відповідь | Помилки |
| --- | --- | --- | --- |
| `POST /referrals` | повне тіло без `id` | `201`, створений запис з `id` | `400` для невалідного поля, зайвого `id` або невідомого поля |
| `GET /referrals` | `limit`, `offset`, необов'язковий `status` | `200`, об'єкт `{items,total,limit,offset}` | `400` для неправильних параметрів |
| `GET /referrals/{id}` | ідентифікатор у шляху | `200`, один запис | `404`, якщо запису немає; `400` для неправильного формату |
| `PUT /referrals/{id}` | повне тіло без `id` | `200`, повністю замінений запис | `400` для невалідного тіла, `404` для відсутнього запису |
| `DELETE /referrals/{id}` | ідентифікатор у шляху | `204` без тіла | `404` для відсутнього або вже видаленого запису |
| `GET /healthz` | без тіла | `200 {"status":"готовий"}` | `503`, якщо запит `SELECT 1` до бази не виконується |

Для переліку `limit` за замовчуванням дорівнює 20, допустимі значення від 1 до 100. `offset` за замовчуванням дорівнює 0. Запит без `status` охоплює всі записи, а `total` рахується до застосування пагінації.

## 3 Dockerfile, .dockerignore і docker-compose.yml

### Dockerfile

```dockerfile
FROM python:3.12-alpine AS builder

WORKDIR /build

RUN apk add --no-cache build-base

COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt

    PYTHONUNBUFFERED=1

    && rm -rf /wheels

CMD ["uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 8 Розрахунки

### 8.1 Прискорення і метрика Карпа Флатта

`S = X₂ / X₁`, де `X₁` і `X₂` - досягнута інтенсивність для однієї та двох реплік. Для `N = 2`:

`e = (1 / S - 0,5) / 0,5`.

| Задано, зап/с | X1 | X2 | S | e |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 10,000 | 10,000 | 1,000 | 1,000 |
| 100 | 100,000 | 100,000 | 1,000 | 1,000 |
| 500 | 348,881 | 488,962 | 1,401516 | 0,427027 |

Для 500 запитів/с:

`S = 488,962355 / 348,881133 = 1,401516`.

`e = (1 / 1,401516 - 0,5) / 0,5 = 0,427027`.

На рівнях 10 і 100 запитів/с обидві конфігурації обмежені заданою інтенсивністю, тому формальне `S = 1` не характеризує межу масштабування. На перевантаженому рівні друга репліка дає приріст близько 40,15%. Значення `e ≈ 0,427` відображає велику частку роботи без виграшу від реплікації: спільну PostgreSQL, Nginx, Docker Desktop і конкуренцію з генератором.

### 8.2 Перевірка закону Літтла

Рівень: 100 запитів/с, одна репліка.

`λ = 100,000 запитів/с`.

`W = 10,415918 мс = 0,010415918 с`.

`L = λ × W = 100 × 0,010415918 = 1,041592 запиту`.

Виміряне генератором середнє число запитів у системі: `1,041592`. Розбіжність: `0,000019%`. Закон Літтла для цього сталого прогону виконується.

### 8.3 Відкритий і закритий контур

Для перевантаженого рівня 500 запитів/с в одній репліці середня кількість запитів у системі дорівнювала приблизно 228. Закритий контур запущено з фіксованою паралельністю 228.

| Контур | Досягнуто, зап/с | p95, мс |
| --- | ---: | ---: |
| Відкритий | 348,881 | 3 985,342 |

У закритому контурі наступний запит з'являється лише після завершення попереднього. Коли сервіс сповільнюється, генератор сам знижує темп і не створює всі запити, які мали б надійти за календарним часом. Тому p95 виглядає меншим, але виміряна пропускна здатність також нижча. Це прояв coordinated omission.

## 10 Додаткова вимога варіанта 2

Фінальний образ базується на `python:3.12-alpine`. Для кожної репліки задано `0.5 CPU` і `384m` пам'яті.

Мережа `backend` має `internal: true`. PostgreSQL оголошує внутрішній порт 5432, але не має секції `ports`, тому він не публікується на хост.

Автоматична перевірка дала:

- підключення з хоста до `127.0.0.1:5432`: недоступне;
- TCP підключення з контейнера `web` до `db:5432`: успішне;
- у `docker compose ps` для PostgreSQL показано лише `5432/tcp` без прив'язки до адреси хоста.

## 13 Відповіді на контрольні питання

1. **PUT і PATCH.** PUT у цій роботі вимагає повне представлення ресурсу й замінює всі змінні поля. PATCH передавав би лише поля, які треба змінити.
2. **Повторний ідентифікатор.** Якщо API дозволяє клієнту задавати ідентифікатор і він уже зайнятий, коректна відповідь - `409 Conflict`. У цьому сервісі `id` генерує база, а переданий клієнтом `id` відхиляється як невалідне тіло з кодом `400`.
3. **Шари образу.** Кожна інструкція створює кешований шар з файловими змінами. Стабільні файли залежностей копіюються раніше за код, тому зміна коду не змушує повторно будувати колеса й установлювати пакети.
4. **Дані після зупинки.** `docker compose down` видаляє контейнери й мережі, але зберігає іменований том. `down -v` видаляє також том. Ручне видалення контейнера бази не видаляє іменований том.
5. **depends_on.** Звичайний `depends_on` контролює порядок запуску процесів, але не готовність PostgreSQL приймати SQL. Потрібні healthcheck і `condition: service_healthy`, а також повторні спроби в застосунку.
6. **EXPOSE і ports.** `EXPOSE` документує внутрішній порт образу й не публікує його. `ports` створює прив'язку на хості. Web знаходить базу за DNS ім'ям сервісу `db` у мережі Compose.
7. **Відкритий і закритий генератори.** Відкритий генератор планує надходження незалежно від відповідей. Закритий має фіксовану кількість клієнтів і під час затримок сам зменшує надходження, через що приховує частину черги.
8. **Ефект другої репліки.** На 500 запитів/с досягнута інтенсивність зросла з 348,881 до 488,962 запитів/с, p95 зменшився з 3,985 до 1,547 с, помилки - з 29,56% до 9,293%. Спільними лишилися PostgreSQL, Nginx і ресурси хоста.
9. **Карп Флатт.** `e ≈ 0,427` означає значну ефективну нерозпаралелену частку. Якби база не була спільною, конкуренція за її пул, CPU, блокування й I/O зменшилася б, тому `e` за інших однакових умов мало б знизитися.
10. **Нелінійне зростання затримки.** Біля межі пропускної здатності нові запити надходять швидше, ніж обслуговуються. Черга накопичується, тому час очікування додається до майже незмінного часу обробки й швидко домінує у p95 та p99.
