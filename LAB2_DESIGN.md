# Проєктування лабораторної №2 (до реалізації)

Джерело вимог: `D:\UNI\мага 1\ВРО\Л2.docx`. Лабораторна розширює CRUD-сервіс лабораторної №1, не змінюючи її результати.

## Архітектура та дані

- `web`: один процес Uvicorn у кожному контейнері, `DB_POOL_SIZE=15`, `asyncpg` pool без overflow, обмеження 0.5 CPU і 384 MiB. `/livez` не звертається до БД; `/healthz` зберігає перевірку БД; `X-Pod` бере `POD_NAME` або hostname.
- HTTP-метрики у `/metrics`: лічильник запитів за методом, шаблоном маршруту й статусом; гістограма секунд із межами 5, 10, 25, 50, 100, 250, 500, 1000 ms; gauge запитів у виконанні. Для невідомого шляху використовуємо сталий шаблон `unmatched`, не фактичний URL. Системні `/metrics` і `/livez` не змішуємо з корисним навантаженням у аналізі.
- Prometheus опитує A-записи `web:8000` кожні 5 s, зберігає дані в іменованому томі. PostgreSQL exporter дає активні/неактивні з'єднання й TPS; паролі передаються через Compose environment.
- Генератор запускається окремим контейнером у frontend-мережі через опублікований nginx порт. Після пілотного виявлення насичення thread pool лабораторної №1 окремий генератор Л2 використовує async I/O без обмеження кількості потоків. Профіль: 10 s warm-up 200 rps, далі кроки 20 s по 200 rps до двох поспіль кроків з досягненням <90% або межі генератора. Створюються 100 тестових записів, ID беруться з seed-файлу. `GET /referrals/{id}`.

## Визначення вимірювань

- Запланована інтенсивність: кількість запланованих стартів у секунду, rps. Фактична відправка: кількість спроб, що дійшли до мережевого виклику за секунду. Успішна пропускна здатність: 2xx **завершення** за секунду. Timeout 5 s входить до non-2xx і паралельно має окремий лічильник; інші транспортні помилки є connection errors. Затримка клієнта: від запланованого часу до завершення або помилки. Усі рядки raw містять плановий, фактичний і кінцевий моменти, статус/тип помилки, затримку.
- Для кроку беремо секунди 6–20 (останні 15 s) за часом завершення. `X(N)` — найбільше середнє успішних завершень цих вікон; дисперсія в таблиці — стандартне відхилення 15 секундних значень. p50/p95/p99 клієнта охоплюють усі завершені спроби; p99 лише 2xx зберігається окремо. Non-2xx fraction рахується з усіх завершених спроб. p99 сервера — гістограма Prometheus, помилка обмежена шириною bucket.
- `G` — максимум середнього успішного потоку контрольних `/noop` кроків. Серія N відкидається з USL, якщо `X(N)>=0.9G` або останній крок досяг >=90% плану. Якщо N=1 обмежено генератором або замало придатних точок, повторити з удвічі меншим CPU web.
- USL: `C(N)=X(N)/X(1)`, `N/C(N)-1 = sigma*(N-1)+kappa*N*(N-1)`. Least squares без intercept; від'ємний коефіцієнт фіксуємо до нуля і повторно оцінюємо інший. У звіті — точки, модель, ідеальна лінія, максимум або асимптота.

## Докази й порядок перевірки

1. Тести: маршрутна нормалізація метрик, `/livez`, налаштування pool і аналіз формул.
2. Docker Compose config, build; лог HTTP для `/livez`, `/healthz`, `/metrics`, CRUD, масштабування до 4 і всі targets UP. SIGTERM під навантаженням — код 0 й відсутність помилок у генератора.
3. Окремий `/noop` контроль; тоді одна серія N=1…4. Raw генератора, Prometheus snapshots, Docker stats, конфігурація Docker/хоста, команди та виводи зберігаються в `results/lab2` без зміни Lab1.
4. Скрипт аналізу відтворює таблиці, USL та графіки лише з raw. `REPORT_L2.md` наводить методику, фактичні результати й обмеження, три допустимі відхилені альтернативи та використання ШІ.

Ризики: обмеження proxy/генератора/хоста можуть не дозволити коректний fit; тоді не видавати його за підтверджений. Графіки не заміняють raw-дані.

## Уточнений протокол після аудиту вимог (до повторної реалізації)

- Кожний профіль `/noop` і N=1…4 — один безперервний запуск генератора: 10 s прогріву при 200 rps, далі 20-секундні кроки без пауз і перезапуску процесу. Raw містить єдину часову вісь та всі запити; X кроку рахується за **усіма** відповідями 2xx, завершеними в останні 15 s кроку, незалежно від того, на якому кроці запит був запланований.
- Профіль `/noop` не має наперед встановленої верхньої межі інтенсивності: він завершується після двох послідовних кроків з X < 0.9 плану. Збережений G — максимум середніх у завершеному профілі. Якщо генератор або хост не дозволить завершити це правило, G не називати встановленою межею.
- Тайм-аут HTTP 5 s входить до non-2xx за умовою завдання; інші транспортні винятки рахуються окремо як connection errors. Raw додатково зберігає тип помилки.
- Клієнтські p50/p95/p99 у фінальному аналізі охоплюють усі завершені спроби (успішні, HTTP non-2xx, timeout і транспортні помилки), від планового часу до результату; p99 тільки 2xx зберігається окремо для діагностики. Це усуває приховування тривалих невдалих запитів.
- Гістограма сервера має **точно** межі набору Г1 (5…1000 ms). Якщо p99 потрапив до `+Inf`, у таблиці зазначається `>1000 ms`, без кінцевої оцінки похибки. Пропускну здатність рахуємо лише з 2xx завершень; основний p99 клієнта — з усіх завершених спроб у відповідному часовому вікні, а successful-only p99 зберігаємо окремо.
- Prometheus зберігає часовий ряд `sum by(instance)(rate(http_requests_total{path="/referrals/{referral_id}"}[15s]))` кожні 5 s поряд із CPU та in-flight кожного web. Графік використовує справжній час неперервного профілю, включно з прогрівом; підписи кроків визначаються з raw.
- Docker stats та завантаження CPU хоста вибираються періодично впродовж профілю. Для кроку X(4) наводиться фактичний знімок у його 15-секундному вікні. Локальне насичення CPU web не оголошується спільним ресурсом між репліками без окремого доказу.
- Повторна серія пишеться в новий каталог `results/lab2_final`, не переписує попередні raw `results/lab2`. Підсумок і графіки перебудовуються тільки з нового raw, Prometheus і ресурсних знімків.
