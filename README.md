# CRUD-сервіс направлень на дослідження

Лабораторна робота 1 з дисципліни «Високопродуктивні розподілені обчислювальні системи». Варіант 2.

## Предметна сутність

Ресурс `referrals` представляє направлення на дослідження.

| Поле | Тип | Обов'язкове | Обмеження |
| --- | --- | --- | --- |
| `id` | ціле число | формується сервером | первинний ключ |
| `patient_code` | рядок до 64 символів | так | непорожній рядок |
| `modality` | рядок | так | `CT`, `MRI`, `XR`, `US` або `PET` |
| `priority` | ціле число | так | від 1 до 5 |
| `doctor` | рядок до 120 символів | так | непорожній рядок |
| `issued_at` | дата | так | формат `YYYY-MM-DD` |
| `status` | рядок | так | `created`, `scheduled`, `completed` або `cancelled` |

Поле `id` відсутнє в запиті на створення та генерується PostgreSQL.

## Контракт API

| Метод і шлях | Призначення | Успішна відповідь | Помилки |
| --- | --- | --- | --- |
| `POST /referrals` | створити направлення | `201` і створений запис | `400` у разі помилки в даних |
| `GET /referrals` | отримати перелік | `200` | `400` у разі неправильних параметрів |
| `GET /referrals/{id}` | отримати один запис | `200` | `404`, якщо запису немає |
| `PUT /referrals/{id}` | повністю замінити запис | `200` | `400` або `404` |
| `DELETE /referrals/{id}` | видалити запис | `204` | `404`, якщо запису немає |
| `GET /healthz` | перевірити доступність PostgreSQL | `200` | `503`, якщо база недоступна |

Параметри переліку:

- `limit`: типове значення 20, допустимий діапазон від 1 до 100;
- `offset`: типове значення 0, мінімальне значення 0;
- `status`: необов'язковий точний фільтр за статусом.

Відповідь зі списком має такий вигляд:

```json
{
  "items": [],
  "total": 0,
  "limit": 20,
  "offset": 0
}
```

## Архітектура проєкту

Проєкт розділено на незалежні `backend` і `frontend`. Backend побудовано за принципами чистої та гексагональної архітектури: прикладні сценарії залежать від порту `ReferralRepository`, а не від `asyncpg` чи FastAPI. PostgreSQL є вихідним адаптером, FastAPI — вхідним адаптером, а `backend/main.py` виконує лише композицію залежностей.

```text
backend/
  domain/       сутності, переліки та порти-інтерфейси
  application/  сценарії CRUD, які залежать від domain
  data/         PostgreSQL-адаптер, пул і конфігурація
  ui/           HTTP-схеми, залежності та маршрути FastAPI
  main.py       композиційний корінь
frontend/
  domain/       правила й довідники предметної області
  data/         адаптер HTTP API
  ui/           DOM-логіка та стилі
  index.html    точка входу вебінтерфейсу
```

Напрям залежностей backend: `ui -> application -> domain <- data`. Шар `domain` не імпортує FastAPI, Pydantic, asyncpg або змінні середовища. Реалізація `PostgresReferralRepository` підставляється в `ReferralService` у композиційному корені.

## Запуск

1. Скопіювати `.env.example` у `.env` і змінити локальний пароль.
2. Зібрати та запустити стенд:

```powershell
docker compose up --build -d
```

3. Перевірити стан сервісу через балансувальник:

```powershell
Invoke-RestMethod http://localhost:8080/healthz
```

Очікувана відповідь: `{"status":"готовий"}`.

Вебінтерфейс доступний за адресою `http://localhost:8080/`, інтерактивна документація API — `http://localhost:8080/docs`.

PostgreSQL і web не публікують порти на хост. Зовні доступний лише порт `8080` балансувальника.

## Горизонтальне масштабування

Запустити дві репліки web-сервісу та оновити балансувальник:

```powershell
docker compose up -d --scale web=2
docker compose restart proxy
```

Перевірити розподіл запитів між репліками:

```powershell
1..10 | ForEach-Object {
    (Invoke-WebRequest http://localhost:8080/healthz).Headers['X-Pod']
}
```

У результаті мають по черзі з'являтися два різні ідентифікатори контейнерів.

## Автоматична перевірка API

```powershell
docker compose --profile test run --rm --no-deps api-test
```

Тест створює тимчасове направлення, перевіряє всі CRUD-операції та коди відповідей, після чого видаляє створені дані.

## Навантажувальне тестування

Повна серія з ЛР1 для 1 і 2 реплік, інтенсивностей 10, 100 і 500 запитів/с, прогріву, трьох повторів та закритого контуру запускається командою:

```powershell
.\scripts\run_benchmarks.ps1
```

Сирі дані зберігаються у каталозі `results/raw`, а компактні медіани й розрахунки — у `results/summary.json`.

Підсумковий опис методики, таблиці вимірювань, розрахунки та відповіді на контрольні питання наведено у [REPORT.md](REPORT.md).

## Поточний стан

Налаштовано PostgreSQL, автоматичне створення таблиці, пул підключень, перевірку `/healthz`, багатостадійний образ і Docker Compose. Backend розділено на `domain`, `application`, `data` та `ui`, а окремий frontend — на `domain`, `data` та `ui`. Реалізовано створення, перелік із пагінацією та фільтром, отримання за ідентифікатором, повну заміну й видалення направлень.

Додано автоматичну перевірку всіх CRUD-операцій. Перевірено, що дані зберігаються після `docker compose down` / `docker compose up -d`, а команда `docker compose down -v` видаляє том і під час наступного запуску створює нову порожню базу. Запущено дві репліки web-сервісу та підтверджено рівномірний розподіл запитів через Nginx. Проведено повну серію навантаження з ЛР1, збережено сирі результати й підготовлено звіт.
